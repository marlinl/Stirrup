# 001 · 数据库 Migration 执行规范

## 1. 目标与范围

自实现 SQLite migration 执行器，负责发现 SQL 文件、验证连续版本、创建迁移索引表、逐版本升级和回退。执行代码位于 `src/sql/`，SQL 位于根目录 `migration/`；不引入 dbmate、Umzug 或 ORM。

本规范是 migration 的权威执行契约；模块与方法实现由 [Design 001](../designs/001_database_migration.md) 定义。[005 · SQLite 存储设计](../005_sqlite_storage_design.md) 负责业务表、数据归属、旧 JSON 导入与备份；[004 · 代码结构](../004_code_structure.md) 负责目录和启动职责。migration 不保存业务数据导入摘要，不承担账号初始化。

## 2. 连续版本链

版本是从 **1** 开始的正整数，不是小数、语义版本或时间戳。0 仅表示尚未应用业务迁移，不写入索引表。版本必须能用 JavaScript 安全整数准确表示。

```text
空库（0） → 1 → 2 → 3 → … → N
升级：只允许 K → K+1
回退：只允许 K → K-1
```

这是逻辑上的单链：前驱由 `version - 1` 唯一确定，不增加 `previous_version`、分支或指针列。禁止跳号、乱序执行、选择任意文件执行、伪造成功记录或自动补齐缺失记录。

- 文件集合必须完整覆盖 `1…N`。
- 数据库已执行集合必须完整覆盖 `1…K`，且 `0 ≤ K ≤ N`。
- 比较的是完整版本集合及文件名，不能只比较数量或 `MAX(version)`。
- 回退后保留全部 SQL 文件。`1,2,3` 回退一次成为 `1,2`，下一次 `up()` 从 3 继续，不生成版本 4 来代表重新执行 3。
- 新增变更文件按目录最大版本 `N+1` 编号，不能因数据库刚回退就重复占用已有文件的版本。

## 3. SQL 文件契约

每个版本必须有一对文件，升级和回退文件使用相同的版本与描述：

```text
migration/
  001_workspace.sql
  001_workspace.down.sql
  002_agents.sql
  002_agents.down.sql
  003_personal_settings.sql
  003_personal_settings.down.sql
```

- `VVV_description.sql` 为 up，`VVV_description.down.sql` 为 down。
- 版本采用至少三位的规范十进制表示：1 为 `001`、10 为 `010`、1000 为 `1000`；禁止 `1`、`0001` 等同值别名。
- 描述匹配 `[a-z][a-z0-9_]*`；版本与描述之间恰好一个下划线。
- 按解析后的数值版本排序，不按文件名字典序排序。
- 一个版本只能有一对文件。重复版本、缺 up/down、描述不配对、无效名称、跳号均报错；未执行的未来版本也必须通过完整校验。
- 仅接受根目录内的普通 UTF-8 SQL 文件；拒绝符号链接、嵌套目录和未知文件，避免静默漏掉脚本。部署时 SQL 清单与代码作为同一版本交付。
- 每个文件至少包含一条有效 SQL 语句；纯空白或纯注释文件无效。
- 每次命令开始时读取并固定完整文件清单及内容快照，命令期间不得重新读到另一套 SQL；部署不可与 migration 并行替换文件。

SQL 只描述本版本的业务结构或数据变化。事务由执行器管理，脚本禁止自行 `BEGIN`、`COMMIT`、`ROLLBACK`、`SAVEPOINT`，禁止修改 `migration` 表、连接 PRAGMA、ATTACH/DETACH、VACUUM 或执行文件/网络等外部副作用。限制应通过 SQLite 授权回调或可靠 SQL 解析实施，不能靠简单关键词正则判定 SQL 安全性。

每个 down 必须把成功执行该版本后的结构恢复为前一版本结构。破坏性数据变化必须在该版本设计中明确可恢复的数据来源；反向 DDL 不能凭空恢复被删除的数据。没有可靠 down 的版本不满足本规范，不能以空文件冒充成功回退。

发布后的文件名与内容不得修改，修正通过追加版本完成。本规范索引表只保存下面三个字段，不提供持久化 checksum；因此只能自动发现文件名不一致，不能识别同名 SQL 内容被修改。代码评审和版本发布必须保证脚本不可变，不宣称具备 Flyway 的 checksum 校验能力。

## 4. 默认索引表

执行器负责创建 `migration`，不把建索引表本身算作版本 1。表名固定，不由业务脚本创建或删除。

```sql
CREATE TABLE migration (
  version    INTEGER PRIMARY KEY CHECK (version > 0),
  created_at INTEGER NOT NULL CHECK (created_at >= 0),
  filename   TEXT NOT NULL UNIQUE CHECK (length(filename) > 0)
) STRICT;
```

| 字段 | 含义 |
| --- | --- |
| `version` | 业务迁移版本号，主键；不使用 AUTOINCREMENT |
| `created_at` | 本次 up 成功登记时的 Unix 毫秒时间戳，事务提交后生效 |
| `filename` | up 文件的完整 basename，例如 `003_personal_settings.sql`，不保存绝对路径 |

索引表只表示**当前仍有效的成功迁移前缀**，不是不可删除的审计日志。不写 pending/failed/down 行，不保存“执行到第几条 SQL”。down 成功删除对应行；再次 up 创建同版本行并使用新的时间戳。

自动初始化规则：

1. 数据库文件不存在或不含用户表的空 SQLite：创建索引表，当前版本为 0。
2. 已存在 `migration`：验证结构、约束、字段类型和全部记录，结构不兼容即报错，不自动改表掩盖问题。
3. 存在业务表但无索引：拒绝把它当空库执行全部 SQL，也不依据业务表猜测已执行版本；旧格式接入见第 10 节。
4. `down()` 回到 0 后保留空索引表与数据库文件，下一次 up 可从 1 执行。

## 5. 对外方法

| 方法 | 输入与职责 | 返回与副作用 |
| --- | --- | --- |
| `check()` | 无目标版本；校验文件集合、索引结构、连续前缀及文件名映射 | 返回 `{ currentVersion: K, latestVersion: N, pendingCount: N-K }`；只读，不创建文件或表。新库按 K=0 返回 |
| `up()` | 校验后顺序应用所有剩余版本，不接受任意版本列表 | 返回同样的状态对象；成功时 K=N、pendingCount=0。按版本逐个提交 |
| `down(targetVersion?)` | 省略时只回退一个版本；指定时要求安全整数 `0 ≤ targetVersion ≤ K` | 按 K、K-1…目标+1 顺序逐个回退；返回状态对象，pendingCount=N-目标 |

`down()` 在 K=0 时无操作；目标等于 K 时无操作。目标大于 K、负数、小数或不安全整数均报错。即使最后无操作，也必须先完整 check，不能绕过损坏记录或缺失文件。

方法失败抛出错误，不返回成功结果。错误必须包含阶段、方向、失败版本和文件名（如适用）、最后已提交版本与可读原因；不输出凭据、SQL 中的数据或业务行内容。后续通过 check 查询实际状态，不能只信任上一次进程内变量。

## 6. check：先验证再计算差额

在任何业务 DDL 执行前完成以下检查：

1. 扫描并固定第 3 节的文件快照，校验配对、唯一性、编号和连续性，得到 N。空集合视为 N=0；独立执行器可以无操作，但服务启动不接受没有初始化脚本的发布包。
2. 读取数据库完整性与索引结构；数据库不存在时按新库处理，不创建文件。损坏数据库拒绝继续。
3. 按版本升序读取全部索引行。第 i 行必须为版本 i（从 1 开始），因此行数应等于最大版本 K。
4. 每个已执行版本必须有对应的 up/down 文件，且 `filename` 与 up 文件名完全一致；K>N 或目录丢失已执行文件立即失败。
5. 验证已存在业务数据的外键一致性，错误时拒绝执行。
6. 只有上述检查全部通过，才计算 `pendingCount = N-K`。

| 文件版本 | 索引版本 | 判定 |
| --- | --- | --- |
| 1,2,3 | 空 | 待执行 3 个 |
| 1,2,3 | 1,2 | 待执行 1 个：3 |
| 1,2,3 | 1,2,3 | 已完成，不执行业务 SQL、不更新时间戳 |
| 1,3 | 1 | 文件跳号，报错，不执行 3 |
| 1,2,3 | 1,3 | 索引断链，报错，不补写 2 |
| 1,2 | 1,2,3 | 数据库领先于发布文件，报错，不自动回退 |
| 1,2,3 | 1,2,3，但版本 2 文件名不同 | 文件名不一致，报错，不能因数量相同就返回完成 |

check 的结果是当时的快照，不能把单独一次 check 当作后续执行的授权；up/down 必须在自身独占区间内重新校验。

## 7. up：顺序升级

1. 获取迁移独占锁，建立文件快照并 check。
2. 对新库创建连接及索引表；索引初始化使用独立事务，失败不留下半张表。建立索引后重新验证。
3. 若 K=N，直接返回成功；不执行脚本或重写现有索引。
4. 对 v=K+1…N 依次执行，每次只处理一个版本：
   - `BEGIN IMMEDIATE`，再次核对当前索引前缀仍为 `1…v-1`。
   - 执行 v 的完整 up SQL。
   - 校验外键和本次变更的数据库完整性。
   - 插入 `(v, 当前时间戳, up文件名)`；插入失败视为整个版本失败。
   - `COMMIT` 成功后才能认为当前版本变为 v，并继续 v+1。
5. 任一步失败则回滚当前版本、立即停止；不运行后续版本，不自动撤销之前已提交的版本。
6. 释放锁与执行资源，返回最终状态或抛出错误。

例如从 2 升级到 5：3 成功、4 失败，则最终索引为 `1,2,3`，4 的业务 SQL 与索引插入全部回滚，5 不执行。下一次 up 重新 check 后从 4 开始。

## 8. down：顺序回退

回退属于显式离线维护操作，不在普通服务启动时触发。调用前停止应用写入。

1. 获取同一独占锁并完整 check，得到 K、N，验证目标。
2. 确认整个回退路径的 down 文件均存在且合法；缺一个就在任何回退之前报错。
3. 对 v=K…目标+1 逆序执行：
   - `BEGIN IMMEDIATE`，再次核对当前索引前缀仍为 `1…v`。
   - 执行 v 的完整 down SQL，恢复 v-1 的结构。
   - 校验外键和数据库完整性。
   - 删除索引中版本 v 的记录，影响行数必须恰好为 1。
   - `COMMIT` 成功后当前版本变为 v-1，才允许处理下一个版本。
4. 任一步失败回滚当前版本，保留该版本索引；已经成功回退的更高版本保持已回退状态。立即停止并释放资源。

例如 `1,2,3,4` 回退到 1：down(4) 成功、down(3) 失败，则最终仍是 `1,2,3`。再次 down(1) 从 3 开始；改为 up() 则从 4 开始。

普通启动总是 up 到文件最大版本。因此维护时回退到 2 后，如果再次使用包含版本 3 的发布包启动，会自动重做 3。需要持续运行旧结构时，必须使用与之匹配的旧代码和完整的 `1…2` 文件集，不能只删当前发布包的高版本文件来强行启动。

## 9. SQLite 事务、互斥与启动

- 每个版本的业务 SQL 与索引写入/删除必须使用**同一连接、同一事务**。禁止先提交 DDL 再单独登记记录。
- up/down 内部的整个检查与执行序列持有基于规范化数据库绝对路径的同一独占锁；不同数据库互不阻塞。所有应用入口和维护工具必须遵循该锁。独立 check 只读、不创建锁，以读事务取得快照，不能代替 up/down 持锁后的复核。SQLite 写事务仍负责实际写入互斥。
- 锁覆盖整个命令，不能每个版本之间释放；冲突明确失败。崩溃遗留锁须核实所有者结束后清理，不因超时就强行删除。
- 迁移连接设置有限 busy timeout。需重建外键相关表时，在事务开始前暂时关闭外键，在事务内执行 `foreign_key_check` 并在失败时回滚，finally 恢复 `foreign_keys=ON`；关闭外键不是跳过校验。
- 普通 DDL 与数据变更必须可事务回滚；禁止把不可事务化操作混入脚本。提交结果不明或进程异常后，重新连接并 check，不能凭内存推断是否成功，也不能自动删除数据库。
- 迁移锁不代表运行中服务的实例锁；升级、回退和旧索引接入前须停止旧服务，部署期间禁止其他业务写入。

服务端从根目录 `.env` 读取 `STIRRUP_DATABASE_PATH`，默认 `.local/web/stirrup.sqlite`。相对路径相对于项目根目录解析，绝对路径直接使用；空值、目录路径或不可访问路径报错。只接受文件型 SQLite，不接受 `:memory:` 或 URL。迁移与业务连接必须使用解析后的同一路径；迁移目录由应用发布根目录定位，不随数据库路径变化。

```text
npm run dev / npm run preview / npm start / 直接服务入口
  → 读取并校验 .env（数据库路径、监听配置）
  → migration.up()（内部 check，初始化索引，逐版本提交）
  → 验证业务结构、完成业务初始化并组装服务
  → listen(host, port)
```

数据库检查或业务初始化失败时，关闭连接、释放锁并以非零状态退出；HTTP 和 ACP 均不得先开放端口。启动入口统一调用，不依赖容易被绕过的 npm pre 钩子。build/check 等不启动服务的命令不应修改数据库。自定义数据库路径及 WAL/SHM 不得通过静态文件托管暴露。

## 10. 旧索引的接入边界

旧格式 `schema_migrations(version, applied_at, legacy_digest)` 不是本规范的 `migration` 表。不能把旧库当作版本 0，也不能把历史版本重新执行一次来补索引。

接入使用显式、一次性的离线转换，不放在常规 up 内隐式修复：

1. 停止服务、建立一致性备份，核验旧索引是 `1…K`、K 不超过文件最大版本，业务结构与旧版本匹配。
2. 由已审核的旧版本映射确认每条记录对应的 up 文件名；确认新配套 down 能作用于旧版本生成的结构，不从表数量猜测版本。
3. 在一个事务内创建 `migration`，复制版本和旧 `applied_at` 到 `created_at`，填入准确的 up 文件名；不执行任何业务 migration。
4. 保留旧 `schema_migrations` 及 `legacy_digest` 作为兼容资料；转换后旧表只读，不参与新执行器的进度判断。新库不创建旧表。
5. 提交前按本规范检查新索引与文件对应关系；失败回滚转换，禁止留下部分索引。已有新索引时不重复导入或自动覆盖。

旧 JSON 导入属于独立业务数据工具，其导入摘要不写入新的 migration 表。必须在实现接入时同步更新旧工具的元数据契约；不能让旧工具继续决定 schema 版本或绕过新执行器。

## 11. 验收标准

1. 新库自动创建索引，逐个执行 1…N；所有记录含正确版本、时间和 up 文件名。
2. 重复 up 不改业务数据、不改已有时间戳，返回 pendingCount=0。
3. 文件跳号、重复版本、缺配对文件、非法命名、索引断链、文件名不一致、数据库版本领先均在执行业务 SQL 前失败。
4. 数量相同但版本集合或文件名不同，不能报告完成。
5. up 中间 SQL 或索引插入失败，当前版本全部回滚，已成功前缀保持，后续版本不执行；重试从当前版本+1开始。
6. down 中间 SQL 或索引删除失败，当前版本结构和索引一起保留；禁止跳过失败版本继续回退。
7. 回退到 0 保留空索引；再次 up 从 1 开始。回退后再次应用同一版本，重新创建时间戳。
8. 多步 down 严格按降序提交；非法目标及缺失 down 在执行前被拒绝。
9. 两个执行者争用同一路径时不能同时迁移；不同路径可以独立执行；失败与异常路径释放资源。
10. 模拟提交前崩溃后，SQL 与索引同时未提交；提交后崩溃重启不得重复应用已提交版本。
11. `.env` 默认、相对、绝对数据库路径解析一致；业务连接和迁移连接不能指向不同库；迁移失败时端口未监听。
12. 完整验证 `0 → N → 0 → N` 的结构恢复，以及各版本 up/down 对数据保留的明确承诺。
13. 旧索引转换不重跑业务 SQL，保留原时间和旧摘要；来源不明、结构不符或转换失败时不生成可用的新索引。

## 12. Flyway 参考与差异

参考 Flyway 的“先读历史表与文件、校验、执行待应用迁移、成功登记”流程及逆序撤销思想：

- [Migrate](https://documentation.red-gate.com/flyway/reference/commands/migrate)
- [Schema history table](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/flyway-schema-history-table)
- [Validate](https://documentation.red-gate.com/flyway/reference/commands/validate)
- [Undo](https://documentation.red-gate.com/flyway/reference/commands/undo)

连续整数、强制配对 down、回退删除当前有效记录是本项目契约，不声称与 Flyway 的历史状态模型一致。本规范不提供 repeatable、out-of-order、repair、跳过执行标记成功或 checksum 校验；不扩展到多数据库驱动。
